**ADR-014 — Browser sessions: backend-for-frontend with httpOnly cookies (Phase 2)** · accepted (to implement) · 2026-11-19
Owner asked for maximal protection against session hijacking and XSS token theft. A bearer token kept in `localStorage` is readable by any injected script. Design: Next.js server (BFF) holds the Supabase session in **`HttpOnly; Secure; SameSite=Strict`** cookies (via `@supabase/ssr`), validates it server-side, and forwards API calls to FastAPI with the bearer token attached **on the server** — the browser JavaScript never sees an access or refresh token. State-changing BFF routes additionally verify the `Origin` header (CSRF). Supabase refresh-token rotation + reuse detection stays on. Backend JWT verification pins the algorithm, checks `aud`/`iss`/`exp`/`nbf`, requires a verified email on the `OWNER_EMAILS` allow-list. The current direct-fetch health call is the only browser→API traffic until this lands (it carries no credentials).

**ADR-015 — Strict nonce-based CSP; Cache Components off** · accepted · 2026-11-19 · **[DEVIATION from scaffold defaults]**
A nonce + `strict-dynamic` policy (no `unsafe-inline` for scripts) is the strongest practical XSS defence but needs per-request rendering. The create-next-app defaults (`cacheComponents`, `partialPrefetching`) prerender a static shell that cannot carry a nonce, so they are disabled; every route is dynamic (`force-dynamic`), the policy is built in `src/proxy.ts`, and the nonce is forwarded to `next-themes` and Base UI's `CSPProvider`. Verified in a real browser: zero violations on the app and 404 page; injected inline scripts, remote scripts, event handlers, `javascript:` links and cross-origin exfiltration are all blocked. `style-src-attr 'unsafe-inline'` (attributes only, cannot run script) is the one deliberate allowance. Trusted Types (`require-trusted-types-for 'script'`) is a candidate future hardening once the dependency tree is confirmed compatible.

**ADR-017 — HTTPS/TLS everywhere, enforced by configuration** · accepted · 2026-11-19

**ADR-018 — Abuse and DoS controls; honest scope** · accepted · 2026-11-19
Implemented: per-client rate limits (Redis sliding-window counter with in-memory fallback so protection survives a Redis outage; stricter buckets for auth/unsubscribe), proxy-aware client IP that cannot be spoofed via `X-Forwarded-For` (N-th entry from the right, `TRUSTED_PROXY_COUNT`), global in-flight cap (fast 503 instead of memory exhaustion; liveness exempt), request-body size limit (declared and streamed, correct 413), DB statement/idle-transaction timeouts, bounded in-memory limiter. **Honest limit:** application code cannot absorb a volumetric network flood; that is the job of the platform edge (Vercel and Render sit behind their own DDoS mitigation). Our responsibility is to stay cheap and bounded behind it. Free-tier note: an attacker who exhausts the free instance can take the service down — acceptable for a personal tool; Cloudflare in front is the upgrade path.

**ADR-024 — No Redis: Postgres is the queue; rate limiting is in-process** · accepted · 2026-11-19 (owner decision) · **[DEVIATION from REQUIREMENTS §2/§15 "Redis + ARQ"]**
Owner asked to run without Redis (cost, and a single always-on service). ADR-002 already made Postgres the source of truth with Redis as mere transport, so the move is clean. (a) **Queue:** a `job_queue` table (task, payload, `dedupe_key` unique, `run_at`, status, attempts/max_attempts, `locked_by`/`locked_until`, last_error) claimed with `FOR UPDATE SKIP LOCKED`; exponential backoff + jitter via `run_at`; a janitor re-queues expired locks; permanent failures go to `dead_letters`; "park until a provider is available" is just a future `run_at`. Workers and the cron-style controller tick run as asyncio tasks inside the single process (`APP_ROLE=all`). Own ~200-line implementation chosen over `procrastinate` so the tables sit under our migrations/RLS guard test and the exactly-once send protocol, with no extra dependency. Polling backs off 1 s → 10 s when idle (also keeps free Supabase from pausing). (b) **Rate limiting:** exact in-memory sliding window (bounded LRU) — correct for one process; resets on restart, acceptable. (c) **Removed:** `arq`, `redis`, `hiredis`, `fakeredis`, `REDIS_URL`, the Redis readiness check/UI card, Redis TLS validators, `dev_redis.py`, CI Redis services. (d) **Consequence:** one process only — no horizontal scaling without reintroducing a shared limiter; accepted for a personal tool (ADR-012). `REQUIREMENTS.md` stays verbatim; this ADR is the recorded deviation. (e) **Supersedes:** the Redis parts of ADR-017/018.

**ADR-028 — Duplicate-aware discovery: no email and no credit is spent on a repeat** · accepted · 2026-11-19 (owner requirement: different searches and platforms return the same leads)
1. **Canonical identity.** Company key = registrable domain (lower-cased, scheme/`www`/path stripped, IDN→punycode via `tldextract`); without a website, normalised name + city + country. Contact key = lower-cased, trimmed e-mail. A chain's branches share one domain ⇒ one company with many locations ⇒ one conversation.
2. **Merge on arrival.** Every provider/search result is normalised and upserted; a repeat never creates a second record. It adds a `lead_sources` provenance row (provider, query, URL, time) and a `discovery_job_results` row with `outcome=duplicate` and `matched_on` (domain | email | name_city | fuzzy). Independent corroboration by ≥2 sources raises confidence.
3. **Spend-aware.** Before calling a credit-limited provider the pipeline checks a **lookup ledger** (provider, normalised input, result hash, expiry): known inputs reuse the stored answer, and *negative* answers ("Hunter found nothing for X") are cached for 30 days — so no credit is spent twice.
4. **Contact guards.** Global suppression; an **"already contacted" check against `email_messages.to_email`** (survives lead deletion) across ALL campaigns within a cooldown (default 180 days); one active contact per company per campaign; Job Hunter and NEXORA data stay separate, suppression is shared.
5. **Database last line of defence** (already in the schema): unique `(workspace, dedupe_key)` on companies, unique contact e-mail, unique `(campaign, company)` leads, unique `(campaign, contact, step)` messages, unique idempotency keys.
6. **Visibility.** Per provider/search *novelty rate* (new vs duplicate) on the Ops page; a search whose novelty collapses is parked or rewritten, and the discovery cursor never re-reads pages already processed.
7. **Tests (Phase 3):** property tests that URL/e-mail variants collapse to one key; cross-provider merge; ledger prevents a second credit spend; cooldown; concurrent discovery of the same company yields exactly one record.

**ADR-030 — Job queue semantics: at-least-once delivery, fenced writes, attempts only consumed by real failures** · accepted · 2026-11-19
Implements ADR-024 (`app/queue/`, table `job_queue`). Everything below is covered by tests against a real PostgreSQL with a fake clock (`tests/integration/test_queue.py`, `test_worker.py`).
1. **Claim.** One statement: `UPDATE … WHERE id IN (SELECT … ORDER BY priority, run_at FOR UPDATE SKIP LOCKED LIMIT n)`. Concurrent workers never block each other and never receive the same row (tested: 60 jobs, 10 racing claimers, zero duplicates). A worker claims only task names it has handlers for.
2. **Lease + heartbeat.** Default lease 60 s, heartbeat every lease/3. A reaper recovers expired leases (crashed/restarted process). A worker whose heartbeat is rejected *cancels its own handler* — a zombie must not keep performing side effects.
3. **Fence.** Every write after a claim must match `(id, locked_by, attempt, status='running')`. A zombie that wakes up after its job was recovered and re-claimed (even by the same worker id) is rejected and cannot overwrite the new owner's outcome.
4. **Attempt accounting.** A handler failure, timeout or **crash** consumes the attempt (a task that kills the process must not loop forever). `ParkJob` ("provider rate-limited / exhausted, retry at T") and graceful shutdown **do not**: a quota that resets tomorrow never dead-letters a healthy task (REQUIREMENTS_AUTONOMY §A).
5. **Retry.** Jittered exponential backoff in `app/core/retry.py` (shared with the provider failover layer); a provider's `Retry-After` is always honoured. Permanent errors and exhausted attempts → status `dead` + an upserted `dead_letters` row (unique per task + payload hash, reopened if it fails again) with Ops-page retry/discard actions.
6. **Dedupe + outbox.** At most one *active* job per `(workspace, dedupe_key)` (partial unique index); enqueueing a duplicate returns the existing job. `enqueue(session=…)` joins the caller's transaction (SAVEPOINT around the conflict), so a state change and its follow-up job commit or roll back together.
7. **Delivery is at-least-once.** Handlers must be idempotent. Exactly-once *sending* is guaranteed by the message state machine and unique constraints (ADR-002, ARCHITECTURE §5), never by the queue.
8. **Cancel** is cooperative (queued → cancelled immediately; running → `cancel_requested`, observed at the next heartbeat via `ctx.raise_if_cancelled()`), and a cancel-requested job is never retried. **Periodic jobs** use dedupe key `periodic:<task>`, so a slow run can't stack copies; a restart enqueues one immediately.
9. **Hygiene.** Persisted error text is scrubbed of credential-shaped strings and bounded to 2 000 chars; `purge_finished` keeps the table small for the 500 MB free tier (succeeded/cancelled 7 d, dead 30 d; dead-letter rows are kept).

**ADR-031 — ProviderManager: capability-based routing, atomic quota, honest credits, no evasion** · accepted · 2026-11-19
Implements REQUIREMENTS_AUTONOMY §B–§E (`app/providers/`). Pure rules in `rules.py`, persistence in `store.py`, orchestration in `manager.py`; tested by 100+ unit tests and 45 integration tests on real Postgres (including a 30-way race on a quota of 10 and a single-probe-after-outage test; both guards were mutation-checked).
1. **Business logic asks for a capability, never a vendor.** `manager.call(Capability.LLM, operation, tier=…, personal_data=…)`. Providers are ordered **free before paid, then by owner priority, then by remaining headroom** (spreads load across free tiers). Paid providers need explicit opt-in *and* a monthly budget.
2. **Atomic quota.** A task reserves quota with one conditional `UPDATE … RETURNING` that re-checks enabled / cooldown / rate-limit / daily / monthly limits, so racing workers cannot overspend and a stale snapshot cannot cause an over-call. Calls the provider did not count (network error, 429, 401/403) are refunded.
3. **Credits are never invented.** `remaining_credits` is set only from provider-reported data (e.g. Groq `x-ratelimit-*` headers) and marked `provider_reported`; otherwise it stays unknown and internal counters are labelled as such. A reported zero blocks only until its reset time (a stale report must not lock a provider out forever).
4. **Error taxonomy drives behaviour.** 429 → wait ≥ `Retry-After` (+jitter), no failure streak. Quota → exhausted until the documented reset (unknown reset ⇒ re-probe hourly). 401 → *needs attention*, not used until the owner fixes it (time does not heal it). 403 is classified (quota / permissions / account / policy / unknown). Transient → bounded in-call retries with backoff, then cooldown with growing backoff; the circuit shows OPEN after 5 failed sequences and recovers through **exactly one** half-open probe. Invalid or permanent responses are never retried or re-routed.
5. **No evasion, by construction.** One credential per provider; no account/key rotation. Sending-capable specs must set `fail_over_on_limits=False` (enforced in `ProviderSpec`): a mailbox limit raises `ProviderLimitReachedError`, never a switch to another mailbox. A **policy refusal** (403/policy) is never shopped around. A **non-idempotent** call that may have been processed (timeout after sending) raises `UncertainOutcomeError` and is reconciled by the caller, never repeated.
6. **Privacy gate.** `ProviderSpec.may_receive_personal_data` defaults to False and is opted in per provider after reading its terms (Groq: Services Agreement §4.2). A call with `personal_data=True` is only routed to cleared providers.
7. **Nothing lost, only the affected task pauses.** When no provider is eligible the manager raises `AllProvidersUnavailableError(next_available_at)`; the handler converts it to `ParkJob` (ADR-030), so the task resumes by itself when the earliest provider returns. Bookkeeping failures after a successful call never discard the result (that would cause a repeat call).
8. **Visibility.** State changes (not every call) go to the activity feed ("groq-smart quota exhausted…", "continued with …"); `overview()` feeds the settings page with real figures and the exact blocking reason. Usage events are retained 30 days (`purge_usage_events`). Error text is scrubbed of credential-shaped strings and the adapter's own key before it is stored.
9. **Groq** = two providers on one key (`groq-smart` / `groq-fast`) because its quotas are per model; a "smart" call is never served by the fast tier (`tier`). Verified live (opt-in `pytest -m live`, never in CI).

**ADR-033 — Browser sessions implemented: same-origin API proxy, hardened `__Host-` cookie, server-side everything (completes ADR-014)** · accepted · 2026-11-19
1. **The browser holds nothing.** Sign-in is a Server Action (`src/app/login/actions.ts`); the Supabase session is written to an `HttpOnly` cookie by a *server-side* client (there is deliberately no browser client, no `NEXT_PUBLIC_*` setting, and `connect-src 'self'`). Every API call goes through `/bff/*`, which attaches the bearer token on the server. Asserted in a real browser: the access and refresh tokens appear in no cookie visible to JS, no storage, no HTML and no response body.
2. **Cookie hardening is enforced, not trusted.** `@supabase/ssr` defaults to `httpOnly:false` and a 400-day lifetime, so every cookie it writes passes through `hardenCookieOptions`: `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, no `Domain`, 7-day sliding lifetime, name `__Host-aoi-session` (the browser itself then refuses sub-domain-planted or insecure copies).

4. **Layered authorisation.** The proxy (`src/proxy.ts`) refreshes the session and redirects optimistically (cheap, also sees prefetches); the dashboard layout calls the backend's `/api/v1/me` — the authority — on every render and leaves the page for anything but "you are the owner" (Next's guidance: do the real check next to the data). Sign-in only *keeps* a session if the backend confirms the owner; an unverified token in a cookie is rejected (tested with a forged, genuinely-shaped session).
5. **The API proxy is a narrow gate** (`src/lib/bff/handler.ts`): fixed destination, only `/api/v1/*` and the two health probes, plain-token path segments (no traversal), browser-supplied `Authorization`/`Cookie` ignored, JSON-only bounded bodies, bounded query, 30 s timeout, upstream redirects never followed, upstream cookies/headers never returned, never cached.
6. **Sign-in hygiene.** One message for every credential failure (no account enumeration); `?next=` accepts only same-site paths (open-redirect tests); `?error=` can only select a fixed message; sign-out revokes the refresh token everywhere (`scope: global`).
7. **How it is tested.** 147 unit tests plus 42 Playwright tests that run the real backend and the real dashboard build against a *fake Supabase Auth* (`frontend/e2e/support/fake-idp.mjs`, which signs genuine ES256 tokens, so no part of login is mocked). The same run found a deployment-breaking defect: `OWNER_EMAILS=a@example.com` crashed the backend at startup (pydantic-settings JSON-decoded the list); fixed with `NoDecode` and covered by a real-environment test.
8. **Not yet built:** TOTP enrolment/challenge UI (backend gate ready), "change password" screen.

**ADR-034 — Gmail connection: dashboard-routed OAuth callback, encrypted PKCE state, encrypted tokens** · accepted · 2026-11-19
Implements ADR-009/013 (`app/integrations/gmail/`, `app/api/gmail.py`, `/settings/integrations`).
1. **The redirect address is a dashboard route** (`/integrations/gmail/callback`), not the API. The owner's `SameSite=Lax` session cookie rides along on that top-level navigation, the route forwards `code` + `state` to the API with the owner's token, and the backend refuses unless the state was issued **to that same user** — which blocks the "trick the owner into linking the attacker's mailbox" attack (mutation-checked: with the check removed, two tests fail). A signed-out visitor is sent to sign in; the one-time code is never carried through the login page.
2. **The `state` is Fernet ciphertext** (authenticated encryption) holding `{user, workspace, mode, PKCE verifier, expiry}`: it cannot be forged or edited, reveals nothing in the URL, expires after 10 minutes, and keeps the PKCE verifier secret from the browser (a verifier in a signed-but-readable state would defeat PKCE). Authorization-code + **PKCE S256 + client secret**; `access_type=offline` and `prompt=consent` so a refresh token always arrives; only `gmail.send`, `gmail.readonly`, `openid`, `email` are requested, and the *granted* scopes are verified (Google lets people untick boxes) — a half-grant is revoked unless the mailbox is already connected (revoking could kill the working grant).
3. **Tokens are Fernet-encrypted at rest** (`oauth_tokens`), never in an API response, log, error, audit row or activity message; error text from Google is scrubbed (it can echo the code). Account summaries have no token fields by construction.
4. **Refresh is automatic and contained.** Access tokens refresh 90 s early, one refresh at a time per mailbox (8 concurrent callers share one Google call). A refresh token Google rejects (`invalid_grant`) puts *only that mailbox* in `needs_reauth`, posts one activity event, and stops further calls; a Google outage leaves the mailbox untouched and recovers by itself. Disconnecting always succeeds locally and revokes at Google best-effort.
5. **Rules kept:** one mailbox serves exactly one mode (a second attempt for the other mode is refused), several mailboxes per mode are allowed (for the Workspace plan), mailboxes are scoped per workspace, and a read-only "test connection" calls Gmail's profile endpoint and sends nothing.
6. **Tests:** 77 backend tests (building blocks, real-database service flows, HTTP API) with a scriptable fake Google; 32 frontend unit tests; browser tests that inspect exactly what is sent to Google's consent screen (scopes, PKCE, opaque state) and exercise forged/declined/incomplete callbacks.


**ADR-035 — Gmail send path: exactly-once sender, reconciler, and mailboxes as identities (not interchangeable providers)** · accepted · 2026-11-20
Implements ARCHITECTURE §5 (`app/integrations/gmail/{mime,api}.py`, `app/services/outreach/sender.py`).
1. **A mailbox is an identity, so Gmail sending does not go through `ProviderManager`.** The manager exists to substitute one provider for another; a prospect must only ever hear from the mailbox the campaign chose, and a sending limit must be waited out, never routed around (ADR-025). The Gmail adapter therefore lives with the Gmail integration, reuses the provider **error taxonomy** (`TransientProviderError.request_may_have_been_processed`, `RateLimitedError`, `QuotaExhaustedError`, …) so the same classification vocabulary applies, and takes its limits from the mailbox row (`daily_limit`, `hourly_limit`, set by the adaptive ramp in Phase 4), not from a static quota table.
2. **Claim and limit check are one transaction.** `send()` locks the message row, then the mailbox row (the mailbox row *is* the lock that serialises every claim for that mailbox), counts the mailbox's rolling hour/24 h sends — **including `SENDING` and `SEND_UNCERTAIN`**, because an unconfirmed send may have spent the slot — and only then flips the message to `SENDING`. Twelve racing workers against a limit of five send exactly five (mutation-checked: without the lock the test fails). A deferred message reports *when* the oldest counted send leaves the window.
3. **The gate runs after the claim**, through an explicit `SendGate` protocol (no default-open implementation exists — Phase 4 supplies the compliance gate and the unsubscribe links/footers it returns in a `Clearance`). A `Refusal` makes the message `SKIPPED` with its reason; a gate that crashes releases the message unconsumed and the error surfaces.
4. **Every write after the claim is fenced** by `claim_token` and the expected status. A worker that lost its claim (reaper, restart, slow call) cannot overwrite the new owner's result (mutation-checked).
5. **Ambiguity is never retried blindly.** The Gmail client distinguishes *never reached Gmail* (connect error → safe to retry later) from *may have been processed* (read timeout, reset, any 5xx, or a 2xx with an unusable body). The latter becomes `SEND_UNCERTAIN`. An unexpected exception after the send call has started leaves the row `SENDING` instead of releasing it — releasing would risk a duplicate (mutation-checked).
6. **The reconciler asks the mailbox** (corrected 2026-11-20, see below). `reconcile()` handles `SEND_UNCERTAIN` and `SENDING` rows older than the 10-minute lease by searching the Sent folder for mail to the same recipient since five minutes before the claim (spam/trash included, at most 20 candidates) and keeping the messages whose `X-AOI-Message` header carries our token. Found → `SENT`, with Gmail's own timestamp and the Message-ID Gmail assigned; found twice → still `SENT`, plus an ERROR event; not found → wait out the 15-minute settle window, then re-queue **once**; a second unconfirmed attempt becomes `FAILED/send_unconfirmed` for the owner to look at. A mailbox that needs reconnecting is simply not decided about.
7. **Sender identity is verified, not trusted.** A `From` other than the mailbox's own address must be a send-as alias Google reports as verified (`settings.sendAs`, covered by the `gmail.readonly` scope we already hold — checked in Google's reference), cached ten minutes; otherwise the message fails with a clear reason instead of Gmail silently sending as the mailbox itself.
8. **Message construction is injection-proof and bounded**: CR/LF/NUL are refused in every header value, addresses must match a strict ASCII pattern (one recipient only), threading ids and unsubscribe URLs are validated (https only; one-click header only with https), non-ASCII text is RFC 2047/quoted-printable encoded, the finished message is capped at 200 KB, and the `Date` header comes from the injected clock.
9. **Failure routing (all tested):** 400/other 4xx → `FAILED gmail_rejected`; 401 → mailbox `needs_reauth`, message released; administrator block / missing scope → mailbox `error`, message released; sending limit → re-check in 1 h (a polling interval, **not** a claimed reset time) with a warning event; 429 → the `Retry-After` it gave, else 5 min; Google token outage → 5 min. Tokens are scrubbed from every stored error.
10. **Not built yet (deliberately):** the queue task handlers that call `send()`/`reconcile()` on a schedule and the real compliance gate (Phase 4, together with app-startup wiring of the queue); inbound sync (Phase 5). **Live verification** against a real mailbox needs the owner to have connected one (ADR-034); the first real send will go to the owner's own address only.


**ADR-036 — Inbox sync: History API polling, a scope guard that never reads private mail, deterministic bounce handling** · accepted · 2026-11-20
Implements ARCHITECTURE §6 (inbound half): `app/integrations/gmail/{inbound,api}.py`, `app/services/inbox/sync.py`.
1. **Scope guard.** The mailboxes also hold the owner's private email, so a message is stored **only** if it (a) is in a Gmail thread of ours (`email_threads`), (b) answers one of our own `Message-ID`s (`In-Reply-To`/`References`), or (c) is a delivery-status notification quoting one of our `Message-ID`s. 2. **Polling, not push, for now.** `InboxSync.poll()` reads `history.list` from a stored cursor (`watch_states.history_id`), pages through it, and advances the cursor only after the whole batch was handled. A `404` (Google keeps history "typically at least a week", sometimes far less) triggers a resync of our own threads and a fresh cursor taken *before* the re-read so nothing arriving meanwhile is lost. The first poll only sets the cursor — nothing before the connection can be a reply to something we sent. Pub/Sub push (and `users.watch` renewal) stays on the list for when the app is deployed and has a public HTTPS endpoint; the poll remains the fallback.
3. **At-least-once with idempotent storage.** Storing a reply is `INSERT … ON CONFLICT DO NOTHING` on `(account_id, gmail_message_id)`; the thread counters are touched only by the insert that won. Four concurrent pollers record six replies exactly once (mutation-checked). A Gmail failure mid-batch keeps what was stored, leaves the cursor, and the next poll skips the stored ones. Gmail ids are only unique *within* a mailbox, so every "already known / ours" lookup is scoped to the mailbox (regression-tested).
4. **Deterministic pre-classification, before any model.** `inbound.py` classifies each stored message as bounce (DSN content type, `mailer-daemon`/`postmaster`, `X-Failed-Recipients`), auto-reply (`Auto-Submitted`, `Precedence`, `X-Autoreply`, subject only as a supplement) or human, extracts the failed recipient / status / quoted `Message-ID` from DSNs, reduces HTML to plain text (tags, scripts and styles removed), strips quoted history, caps what is kept (8 000 characters, 60 MIME parts, depth 8) and keeps only an allow-list of headers. Text is data: prompt-injection phrasing is stored verbatim and never interpreted here.
5. **Bounce bookkeeping.** A matched hard bounce (class 5 except 5.2.2 "mailbox full") sets `bounced_at`/`bounce_kind` on our message and adds a `hard_bounce` suppression entry — **only for the address we actually mailed** and only if the notification names that address (or none); soft bounces are recorded and never suppress. Forged notifications that quote no message of ours are ignored (all tested).
6. **Not decided here.** `incoming_replies` rows start `PENDING`: classification (rules → model → `NEEDS_REVIEW`), stopping follow-ups, lead status, notifications, and unsubscribe handling belong to reply processing (Phase 5 proper). Until then the Phase 4 send gate stops follow-ups by checking `incoming_replies` for the lead — the data it needs is already written. The owner's own manual answers from Gmail (labelled `SENT`, or from the mailbox address) are counted but never recorded as inbound replies.
7. **Live verification** needs a connected mailbox (ADR-034); the first live poll will only initialise the cursor.

**ADR-038 — The only way the application fetches a third-party web page: an SSRF-guarded, polite fetcher** · accepted · 2026-11-20
`app/integrations/web/ssrf.py`, `app/integrations/web/fetcher.py`. Lead discovery reads websites named by directories, search results and scraped pages; any of them can name an internal address, so nothing may call `httpx.get(url)` on such a URL (fixed-host provider APIs excepted).
1. **Decide on addresses, not spellings.** A URL is accepted only for `http`/`https` on ports 80/443 with no credentials. Verified: the name is resolved once per request, and only the pinned address appears on the wire.

The user-agent is generic (`aoi-outreach/0.1`): no personal details.

1. **Business logic never imports a vendor.** It builds a `PlaceQuery` / asks `domain_contacts` / `verify_email` / `web_search` through the ProviderManager (free-first, priority, quota, failover all inherited from ADR-031). Vendor data is untrusted: types are checked field by field, URLs must be http(s), addresses must be syntactically valid, free text is length-capped, and fields we have no use for or no right to use (LinkedIn/Twitter handles, phone numbers from Hunter) are dropped at the boundary.
2. **One request helper** (`HttpProvider`) turns every transport failure and HTTP status into the provider taxonomy (connect failures are safe to retry; anything later is "may have been processed"), refuses non-HTTPS, and **scrubs the real secret values from any text it raises**. Adapters refine only what their vendor does differently: Hunter's usage-limit body, Verifalia's 402, MailboxValidator's error object (also when delivered inside a 200 — never mistaken for a verdict), Brave's **HTTP 422 for an invalid key** (found on the live service; mutation-checked).
3. **Keys stay out of logs.** Where the vendor allows it the key travels in a header (Hunter `X-API-KEY`, Tavily/Brave headers, Verifalia Basic auth); Geoapify and MailboxValidator only accept it in the query string, so `httpx`/`httpcore` loggers are pinned to WARNING in `configure_logging` (tested) and error text is scrubbed.
4. **Conservative verdicts.** MailboxValidator `is_verified: null` is `unknown`, not deliverable; an unrecognised Verifalia class is `unknown`; disposable is `risky`. Only a vendor's explicit positive counts as deliverable. (Verification is *evidence*; compliance rules decide what is sendable.)
5. **Privacy gate.** Only the two verifiers are cleared for personal data (`may_receive_personal_data`), because verifying an address necessarily discloses it to the vendor the owner chose for that purpose; nothing but the address is ever sent. Search and discovery calls carry no prospect data. Brave is `tier="transient"`: results may be used to choose a page, never stored.
6. **Tests = observed shapes.** 91 unit tests use the real responses captured on 2026-11-20 (fictional data, `example.*` domains), including the real error formats; 6 opt-in live tests re-run each adapter against the real service (about six credits in total); 10 mutation checks (key placement, scrubbing, input validation, verdict rules, the Brave quirk, credit reporting).
7. **ZeroBounce and Abstract (added 2026-11-20, after the owner activated ZeroBounce's credits and the key check showed Abstract had been renamed).** Both built from observed responses: ZeroBounce reports failures as HTTP 200, so an error body is resolved with the free credit check (`-1` bad key / `0` empty) before anything is raised; both drop the personal data they return (names, location, breach history). Verdicts are conservative: only ZeroBounce `valid` or Abstract `deliverable` (and not catch-all/disposable) is deliverable; spam traps and abuse are undeliverable; role-based and catch-all are risky. 60 tests, 8 mutation checks, and live tests for both pass.
8. **Not built yet:** Firecrawl, Companies House, Adzuna, Jooble, PDL; the discovery pipeline that uses these (dedupe/merge ADR-028, own MX/disposable/role checks, website crawl, persistence, queue tasks).


**ADR-040 — Discovery core: canonical identity, published-only contact extraction, free mail checks (and what the first live run showed)** · accepted · 2026-11-20
`app/domain/identity.py`, `app/integrations/web/extract.py`, `app/integrations/dns_checks.py`; demo `backend/scripts/live_discovery_demo.py`.
1. **Identity (ADR-028, pure functions).** A company is its registrable domain (scheme, `www`, port, path, case, IDN all collapse; a chain's branches share one company), else normalised name + city + country (accents, punctuation and legal suffixes removed). A contact is its lower-cased address; for *matching only*, Gmail's dots and `+tags` are ignored. **Shared hosts are separate companies**: the public-suffix list is used *with* its private section, otherwise every business on wixsite.com / github.io / blogspot.com would merge into one and real leads would be silently dropped (caught by a test; mutation-checked).
2. **Only published addresses are ever extracted, with provenance.** From a company's *own* pages: `mailto:` links, text a visitor can read, Cloudflare-"protected" addresses (decoded exactly as a browser shows them — verified on a real page), JSON-LD `email`, and the obfuscations people write on purpose (`name [at] host [dot] com`). Scripts, styles, comments and `<noscript>` are not visible text. Template placeholders ("you at yourdomain"), tracking tokens and image-file names that contain an at-sign are dropped. **Nothing is ever invented from a name and a pattern** (a guessed address is never verified, never sent to).
3. **Which pages to read** is decided from links on the page itself: same-site only, contact/about/team/impressum-style, never off-site, non-HTML, or anything the SSRF guard (ADR-038) refuses — including an internal address dressed up as a link.
4. **Free checks before any vendor credit** (cheapest first, docs/PROVIDERS.md §3): syntax → role / free-mail / disposable → **MX lookup** (RFC 5321/7505: MX, implicit MX via A/AAAA, *null MX* and no-mail-server are certain, free rejections). A resolver problem is "could not tell", never a rejection (mutation-checked).
5. **First live run (2026-11-20, Austin dentists, 6 businesses, one Geoapify credit):** 3 of 6 listed no website at all; of the 3 sites read, 2 were read (3 pages each, robots.txt honoured) and **1 published an address** (also the one OpenStreetMap had, correctly decoded from Cloudflare protection); the other publishes a contact form only. Honest conclusion: free sources give **sparse yield (~1 address per 6 businesses)** — the funnel needs (a) a web search (Tavily/Brave) to find the website of businesses that list none, (b) Hunter for domain contacts on promising companies, and (c) acceptance that many small businesses simply cannot be reached by e-mail (those become "form-only" leads, not guesses).
6. **Tests:** 73 identity tests (incl. property tests), 60 extraction tests (incl. hostile HTML, size bound, SSRF-unsafe links), 21 DNS tests; 12 mutation checks.
7. **Not built yet:** persistence and merge into `companies`/`contacts`/`lead_sources` with the lookup ledger, queue tasks for the pipeline (search → enrich → verify), website discovery by search, Hunter/Verifalia orchestration, the compliance gate and campaigns (Phase 4).
